## 最佳实践

### Dragonfly 和 Harbor
  完全可以混合使用，而且这是业界非常常见的组合方案。两者解决的是不同层面的问题，天然互补。

  定位区别

  ┌──────────┬────────────────────┬──────────────────────────────────────────────────────┐
  │   项目   │        角色        │                      解决的问题                      │
  ├──────────┼────────────────────┼──────────────────────────────────────────────────────┤
  │ Harbor   │ 镜像仓库（Registry │ 镜像存储、权限管理、安全扫描、镜像签名、多租户、镜像 │
  │          │ ）                 │ 复制                                                 │
  ├──────────┼────────────────────┼──────────────────────────────────────────────────────┤
  │ Dragonfl │ P2P 镜像分发加速   │ 大规模集群下镜像拉取的带宽瓶颈、分发效率             │
  │ y        │                    │                                                      │
  └──────────┴────────────────────┴──────────────────────────────────────────────────────┘

  典型架构

                      ┌──────────────┐
                      │   Harbor     │  (镜像仓库 / 源站)
                      └──────┬───────┘
                             │
                      ┌──────▼───────┐
                      │  Dragonfly   │  (Scheduler + Seed Peer)
                      │  Supernode   │
                      └──────┬───────┘
                             │
                ┌────────────┼────────────┐
                │            │            │
          ┌─────▼────┐ ┌────▼─────┐ ┌────▼─────┐
          │ Dragonfly │ │ Dragonfly│ │ Dragonfly│  (各节点 Peer / Dfdaemon)
          │  Peer #1  │ │  Peer #2 │ │  Peer #N │
          └─────┬────┘ └────┬─────┘ └────┬─────┘
                │            │            │
          ┌─────▼────┐ ┌────▼─────┐ ┌────▼─────┐
          │containerd │ │containerd│ │containerd│  (容器运行时)
          └──────────┘ └──────────┘ └──────────┘

  工作流程：
  1. containerd 拉镜像时，请求被 Dragonfly 的 Dfdaemon（以 proxy 或 mirror 模式）拦截
  2. Dragonfly Scheduler 调度，第一个节点从 Harbor 拉取（回源）
  3. 后续节点通过 P2P 从已有 Peer 获取镜像块，大幅减少 Harbor 的出口带宽压力

  业界最佳实践

  1. 分层职责清晰

  - Harbor 负责：镜像生命周期管理、RBAC、漏洞扫描 (Trivy)、镜像签名
  (Cosign/Notary)、跨区域复制
  - Dragonfly 负责：加速分发、P2P 传输、预热 (Preheat)

  2. 利用 Harbor 的 Preheat（预热）集成

  Harbor 2.x 原生支持 Dragonfly 预热功能：
  - 在 Harbor 管理界面中配置 Dragonfly 作为 P2P Provider
  - 配置预热策略：当镜像 push 到 Harbor 时，自动通知 Dragonfly 预热到 Seed Peer
  - 这样在大规模部署前镜像就已经缓存好，拉取近乎即时

  3. 多集群 / 多区域部署

  Region A                          Region B
  ┌─────────────┐  ← 镜像复制 →   ┌─────────────┐
  │  Harbor-A   │                  │  Harbor-B   │
  └──────┬──────┘                  └──────┬──────┘
         │                                │
  ┌──────▼──────┐                  ┌──────▼──────┐
  │ Dragonfly-A │                  │ Dragonfly-B │
  │  (集群内P2P) │                  │  (集群内P2P) │
  └─────────────┘                  └─────────────┘
  - 每个区域部署独立的 Harbor + Dragonfly
  - Harbor 之间通过 Replication 同步镜像
  - Dragonfly 只在区域内做 P2P，避免跨区域流量

  4. 配置要点

  containerd 配置 Dragonfly 作为 mirror：
  # /etc/containerd/config.toml
  [plugins."io.containerd.grpc.v1.cri".registry.mirrors."harbor.example.com"]
    endpoint = ["http://127.0.0.1:65001"]  # Dfdaemon 代理端口

  Harbor 中配置 Preheat Provider：
  - 系统管理 → P2P Preheat → 添加 Dragonfly 实例地址

  5. 适用场景判断

  ┌────────────────────────────┬──────────────────────────────────────────┐
  │            场景            │                 推荐方案                 │
  ├────────────────────────────┼──────────────────────────────────────────┤
  │ 集群 < 50 节点             │ 单独 Harbor 即可，P2P 收益不明显         │
  ├────────────────────────────┼──────────────────────────────────────────┤
  │ 50-500 节点                │ Harbor + Dragonfly，显著减少带宽         │
  ├────────────────────────────┼──────────────────────────────────────────┤
  │ 500+ 节点 / 大镜像频繁更新 │ Harbor + Dragonfly 必备，建议加预热      │
  ├────────────────────────────┼──────────────────────────────────────────┤
  │ 多区域部署                 │ 每区域 Harbor（复制） + Dragonfly        │
  ├────────────────────────────┼──────────────────────────────────────────┤
  │ AI/大模型镜像 (10GB+)      │ Dragonfly 收益极大，P2P 分发效率提升数倍 │
  └────────────────────────────┴──────────────────────────────────────────┘

  6. 其他实践要点

  - 监控：Dragonfly 暴露 Prometheus metrics，建议监控回源率、P2P 命中率、分发耗时
  - 降级：配置 Dragonfly 故障时直接回源到 Harbor，保证可用性
  - 镜像清理：Harbor 的 GC 策略与 Dragonfly 缓存 TTL 需要协调，避免 Dragonfly 缓存了已被
  Harbor 清理的镜像
  - 安全：Harbor 做认证鉴权，Dragonfly 需要配置 Harbor 的凭据才能回源拉取

  总结

  Harbor + Dragonfly 是 CNCF
  生态中经过大量生产验证的组合（字节跳动、蚂蚁集团、京东等都在用）。两者不是竞争关系，而是
  仓库层 + 分发加速层 的互补关系。集群规模越大、镜像越大，这个组合的价值越明显。
