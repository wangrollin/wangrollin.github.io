
## K8s 节点上的核心进程

  Master 节点（Control Plane）

  运行 4 个核心进程：

  ┌─────────────────────────┬─────────────────────────────────────────────────────────────────────────────────┐
  │          进程           │                                      作用                                       │
  ├─────────────────────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ kube-apiserver          │ 集群的"前门"，所有组件通信的唯一入口（REST API）                                │
  ├─────────────────────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ etcd                    │ 分布式 KV 存储，保存整个集群的状态数据                                          │
  ├─────────────────────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ kube-scheduler          │ 监听未调度的 Pod，决定它们该跑在哪个节点上                                      │
  ├─────────────────────────┼─────────────────────────────────────────────────────────────────────────────────┤
  │ kube-controller-manager │ 运行各种控制器循环（Deployment、ReplicaSet、Node 等），驱动实际状态趋向期望状态 │
  └─────────────────────────┴─────────────────────────────────────────────────────────────────────────────────┘

  可选：cloud-controller-manager — 如果跑在云上（AWS/GCP/Azure），负责与云 API 交互（负载均衡、存储卷、节点生命周期等）。

  Worker 节点

  运行 3 个核心进程：

  ┌────────────┬──────────────────────────────────────────────────────────────────────────┐
  │    进程    │                                   作用                                   │
  ├────────────┼──────────────────────────────────────────────────────────────────────────┤
  │ kubelet    │ 节点上的"代理人"，接收 API Server 下发的 PodSpec，确保容器按预期运行     │
  ├────────────┼──────────────────────────────────────────────────────────────────────────┤
  │ kube-proxy │ 维护节点上的网络规则（iptables/ipvs），实现 Service 的虚拟 IP 和负载均衡 │
  ├────────────┼──────────────────────────────────────────────────────────────────────────┤
  │ 容器运行时 │ 实际拉镜像、起停容器的进程（containerd / CRI-O）                         │
  └────────────┴──────────────────────────────────────────────────────────────────────────┘

  最小集群的进程全景

  Master Node                          Worker Node
  ┌─────────────────────────┐          ┌─────────────────────┐
  │  kube-apiserver          │          │  kubelet             │
  │  etcd                    │◄────────►│  kube-proxy          │
  │  kube-scheduler          │          │  containerd          │
  │  kube-controller-manager │          │                      │
  │                          │          │  [用户 Pod 进程...]   │
  │  kubelet  ←(Master也跑)  │          └─────────────────────┘
  │  kube-proxy              │
  │  containerd              │
  └─────────────────────────┘

  ▎ Master 节点本身也运行 kubelet + kube-proxy + 容器运行时，因为控制面组件通常以 Static Pod 方式部署（由 kubelet 管理）。

  总结：最精简地看，Master 跑 7 个进程（4 控制面 + 3 节点级），Worker 跑 3 个进程。这些进程协作，就撑起了整个 K8s 集群。

## K8s 进程间通信协议

  核心原则：一切经过 API Server

  etcd ◄──── gRPC ────► kube-apiserver ◄──── HTTPS/REST ────► kubelet
                              ▲                                kube-proxy
                              │                                scheduler
                              │                                controller-manager
                        所有组件都只和
                        API Server 通信

  各通信链路详解

  ┌────────────────────────────────┬──────────────────────────┬───────────────────────────────────────────┐
  │            通信路径            │           协议           │                   说明                    │
  ├────────────────────────────────┼──────────────────────────┼───────────────────────────────────────────┤
  │ kubectl → apiserver            │ HTTPS (REST/JSON)        │ 用户操作入口，标准 RESTful API            │
  ├────────────────────────────────┼──────────────────────────┼───────────────────────────────────────────┤
  │ scheduler → apiserver          │ HTTPS (REST/JSON)        │ Watch 未调度 Pod，写回调度结果            │
  ├────────────────────────────────┼──────────────────────────┼───────────────────────────────────────────┤
  │ controller-manager → apiserver │ HTTPS (REST/JSON)        │ Watch + 更新资源状态                      │
  ├────────────────────────────────┼──────────────────────────┼───────────────────────────────────────────┤
  │ kubelet → apiserver            │ HTTPS (REST/JSON)        │ 上报节点/Pod 状态，拉取 PodSpec           │
  ├────────────────────────────────┼──────────────────────────┼───────────────────────────────────────────┤
  │ kube-proxy → apiserver         │ HTTPS (REST/JSON)        │ Watch Service/Endpoints 变化              │
  ├────────────────────────────────┼──────────────────────────┼───────────────────────────────────────────┤
  │ apiserver → etcd               │ gRPC (HTTP/2 + protobuf) │ 唯一能直接读写 etcd 的组件                │
  ├────────────────────────────────┼──────────────────────────┼───────────────────────────────────────────┤
  │ apiserver → kubelet            │ HTTPS                    │ 反向连接：kubectl exec/logs/port-forward  │
  ├────────────────────────────────┼──────────────────────────┼───────────────────────────────────────────┤
  │ kubelet → 容器运行时           │ gRPC (CRI 接口)          │ 通过 Container Runtime Interface 管理容器 │
  └────────────────────────────────┴──────────────────────────┴───────────────────────────────────────────┘

  几个关键点

  1. API Server 是唯一的 Hub
  - 其他组件之间不直接通信，全部通过 API Server 中转
  - 这是 K8s 的星形架构设计，简化了认证和审计

  2. 两种 gRPC 场景
  apiserver ──gRPC──► etcd          # 高性能 KV 读写，protobuf 序列化
  kubelet   ──gRPC──► containerd    # CRI 标准接口：RunPodSandbox, CreateContainer...
  选 gRPC 的原因：高频调用、强类型、流式通信、性能优于 JSON

  3. Watch 机制（长连接）
  kubelet/scheduler/controller ──HTTP Long Poll / Watch──► apiserver
  - 组件不是轮询，而是通过 Watch 建立长连接
  - API Server 有变更时实时推送（基于 HTTP chunked response）
  - 这是 K8s 响应速度的关键

  4. 所有 HTTPS 通信都有双向 TLS（mTLS）
  每个组件都有自己的证书 ──► apiserver 验证客户端证书
  apiserver 也有证书     ──► 组件验证 server 身份

  一句话总结

  ▎ 对外统一 HTTPS/REST + JSON，内部高性能路径用 gRPC + protobuf，所有流量以 API Server 为中心，mTLS 保证安全。

## Watch 机制与 HTTP Chunked Response

  一、为什么需要 Watch

  方案A：轮询                          方案B：Watch
  ┌────────┐  每秒请求  ┌──────────┐   ┌────────┐  建一次连接  ┌──────────┐
  │ kubelet │──────────►│apiserver │   │ kubelet │────────────►│apiserver │
  │         │◄──────────│          │   │         │◄────────────│          │
  └────────┘ 99%无变化  └──────────┘   └────────┘  有变化才推  └──────────┘

  大量无效请求，浪费资源                   实时 + 高效

  二、Watch 机制详解

  基本流程

  1. 客户端发起 Watch 请求
     GET /api/v1/pods?watch=true&resourceVersion=1234
                                      ↑
                            从这个版本之后的变更推给我

  2. API Server 不关闭连接，持续推送事件流：

     {"type":"ADDED",    "object":{"metadata":{"resourceVersion":"1235"}, ...}}
     {"type":"MODIFIED", "object":{"metadata":{"resourceVersion":"1236"}, ...}}
     {"type":"DELETED",  "object":{"metadata":{"resourceVersion":"1237"}, ...}}
     ...（连接保持打开）

  事件类型

  ┌──────────┬────────────────────────────────────────────────────────┐
  │   type   │                          含义                          │
  ├──────────┼────────────────────────────────────────────────────────┤
  │ ADDED    │ 新资源创建                                             │
  ├──────────┼────────────────────────────────────────────────────────┤
  │ MODIFIED │ 资源被更新                                             │
  ├──────────┼────────────────────────────────────────────────────────┤
  │ DELETED  │ 资源被删除                                             │
  ├──────────┼────────────────────────────────────────────────────────┤
  │ BOOKMARK │ 心跳，告知客户端当前 resourceVersion（不携带完整对象） │
  ├──────────┼────────────────────────────────────────────────────────┤
  │ ERROR    │ 出错，客户端需要重新 List + Watch                      │
  └──────────┴────────────────────────────────────────────────────────┘

  resourceVersion 的作用

  时间线：
    rv=100    rv=101      rv=102       rv=103
      │         │           │            │
    Pod创建   Pod更新标签  Pod扩容      Pod删除

  客户端断线时 rv=101，重连后：
    GET /api/v1/pods?watch=true&resourceVersion=101

  API Server 从 etcd 的变更历史中回放 rv=102、103 的事件
    → 客户端不会丢失任何变更

  Watch 的完整容错模式（List-Watch）

  ┌─────────────────────────────────────────────┐
  │            客户端启动                         │
  │                │                             │
  │    ┌───────────▼───────────┐                 │
  │    │  LIST 全量获取资源列表  │                 │
  │    │  记录 resourceVersion  │                 │
  │    └───────────┬───────────┘                 │
  │                │                             │
  │    ┌───────────▼───────────┐                 │
  │    │  WATCH 增量监听变更    │◄──── 重连回到此处 │
  │    └───────────┬───────────┘                 │
  │                │                             │
  │         连接断开/过期？                        │
  │           │        │                         │
  │        rv有效    rv过期(410 Gone)             │
  │           │        │                         │
  │        从rv重连   回到 LIST 重新全量           │
  └─────────────────────────────────────────────┘

  三、HTTP Chunked Transfer Encoding

  这是 Watch 能"持续推送"的底层传输机制。

  普通 HTTP vs Chunked

  普通 HTTP 响应：                    Chunked 响应：
  ┌──────────────────────┐           ┌──────────────────────┐
  │ HTTP/1.1 200 OK      │           │ HTTP/1.1 200 OK      │
  │ Content-Length: 500   │           │ Transfer-Encoding:   │
  │                      │           │   chunked            │
  │ [500字节完整body]     │           │                      │
  └──────────────────────┘           │ (没有 Content-Length) │
                                     └──────────────────────┘
  服务端必须提前知道                    不需要提前知道总大小
  总大小才能发送                        边产生边发送

  Chunked 编码格式

  HTTP/1.1 200 OK
  Transfer-Encoding: chunked

                       ┌─── 十六进制的 chunk 大小
                       ▼
                      4e\r\n
                      {"type":"ADDED","object":{...}}\r\n     ← chunk 数据
                      52\r\n
                      {"type":"MODIFIED","object":{...}}\r\n  ← 又一个 chunk
                      ...
                      (连接保持打开，随时可以发下一个 chunk)
                      ...
                      0\r\n                                    ← 大小为0 = 结束
                      \r\n

  每个 chunk 的结构

  <chunk-size-hex>\r\n
  <chunk-data>\r\n

  示例：
  1a\r\n                    ← 0x1a = 26 字节
  abcdefghijklmnopqrstuvwxyz\r\n

  为什么 Chunked 适合 Watch

  传统请求：
    客户端 ──req──► 服务端
    客户端 ◄──完整resp── 服务端
    连接关闭 ✕

  Chunked 长连接：
    客户端 ──req──► 服务端
    客户端 ◄──chunk1── 服务端    （Pod A 创建了）
    客户端    等待...   服务端    （什么都没发生）
    客户端 ◄──chunk2── 服务端    （Pod B 更新了）
    客户端 ◄──chunk3── 服务端    （Pod A 删除了）
    ...连接一直开着...

  关键优势：
  - 不需要预知总大小 — 事件流是无限的
  - 实时性 — 每个事件产生后立刻作为一个 chunk 发出
  - 复用标准 HTTP — 不需要 WebSocket 等额外协议，通过普通 HTTP/1.1 就能实现服务端推送
  - 中间设施友好 — 代理、负载均衡器天然支持 chunked encoding

  四、完整数据流

  etcd 数据变更
       │
       ▼ (gRPC Watch Stream)
  API Server 的 watch cache
       │
       ▼ 序列化为 JSON
  HTTP Chunked Response
       │
       ▼ 每个事件 = 一个 chunk
  客户端（kubelet/scheduler/controller）
       │
       ▼ 反序列化，更新本地 Informer 缓存
  触发对应的事件处理函数

  ▎ 总结：Watch 是 K8s 的"神经系统"——API Server 通过 HTTP Chunked 长连接实时推送资源变更，客户端用 List-Watch + resourceVersion 保证不丢事件，整套机制建立在标准 HTTP 之上，简洁而高效。

## HTTP Chunked Response vs WebSocket

  一、本质区别

  HTTP Chunked Response                    WebSocket
  ┌────────┐    HTTP请求    ┌────────┐     ┌────────┐  HTTP升级握手  ┌────────┐
  │ Client │──────────────►│ Server │     │ Client │──────────────►│ Server │
  │        │◄──chunk──────│        │     │        │  101 Switching │        │
  │        │◄──chunk──────│        │     │        │◄──────────────│        │
  │        │◄──chunk──────│        │     │        │               │        │
  │        │              │        │     │        │◄──frame──────│        │
  │        │  单向推送     │        │     │        │──frame──────►│        │
  │        │              │        │     │        │◄──frame──────│        │
  └────────┘              └────────┘     │        │  双向通信      │        │
                                         └────────┘              └────────┘
      还是 HTTP 协议                          升级为独立的 WS 协议

  二、详细对比

  通信模型

  ┌───────────────┬──────────────────────────────────┬───────────────────────────────────────┐
  │     维度      │           HTTP Chunked           │               WebSocket               │
  ├───────────────┼──────────────────────────────────┼───────────────────────────────────────┤
  │ 方向          │ 单向：服务端→客户端              │ 全双工：双向随时发                    │
  ├───────────────┼──────────────────────────────────┼───────────────────────────────────────┤
  │ 协议          │ 标准 HTTP/1.1                    │ 独立协议 ws:// / wss://               │
  ├───────────────┼──────────────────────────────────┼───────────────────────────────────────┤
  │ 连接建立      │ 普通 HTTP 请求                   │ HTTP 升级握手 → 协议切换              │
  ├───────────────┼──────────────────────────────────┼───────────────────────────────────────┤
  │ 请求-响应模型 │ 仍是一次请求对应一个（超长）响应 │ 脱离请求-响应模型，任意一方随时发消息 │
  └───────────────┴──────────────────────────────────┴───────────────────────────────────────┘

  数据格式

  HTTP Chunked:                         WebSocket:
  ┌─────────────────────┐               ┌─────────────────────┐
  │ 1a\r\n              │               │ 0x81 0x05           │ ← 帧头
  │ {"event":"update"}  │               │ Hello               │ ← 负载
  │ \r\n                │               └─────────────────────┘
  └─────────────────────┘                 二进制帧，支持文本/二进制
    纯文本，每个chunk有                     有 opcode 区分消息类型
    十六进制长度前缀                        内置 ping/pong 心跳帧

  基础设施兼容性

  ┌────────────┬───────────────────────┬──────────────────────────────┐
  │    维度    │     HTTP Chunked      │          WebSocket           │
  ├────────────┼───────────────────────┼──────────────────────────────┤
  │ 代理/CDN   │ 天然支持（就是 HTTP） │ 需要代理显式支持 WS 升级     │
  ├────────────┼───────────────────────┼──────────────────────────────┤
  │ 防火墙     │ 80/443 端口，无障碍   │ 部分企业防火墙会拦截升级请求 │
  ├────────────┼───────────────────────┼──────────────────────────────┤
  │ 负载均衡   │ 标准 HTTP LB 即可     │ 需要支持长连接 + WS 的 LB    │
  ├────────────┼───────────────────────┼──────────────────────────────┤
  │ 浏览器缓存 │ 可被中间缓存干扰      │ 不经过 HTTP 缓存层           │
  └────────────┴───────────────────────┴──────────────────────────────┘

  连接管理

  ┌──────────┬────────────────────────────┬───────────────────────────────────┐
  │   维度   │        HTTP Chunked        │             WebSocket             │
  ├──────────┼────────────────────────────┼───────────────────────────────────┤
  │ 心跳     │ 无内置机制，需应用层自己做 │ 协议内置 ping/pong 帧             │
  ├──────────┼────────────────────────────┼───────────────────────────────────┤
  │ 断线感知 │ 依赖 TCP 超时，较慢        │ ping/pong 快速检测                │
  ├──────────┼────────────────────────────┼───────────────────────────────────┤
  │ 重连     │ 客户端重新发 HTTP 请求     │ 客户端重新握手（应用层实现）      │
  ├──────────┼────────────────────────────┼───────────────────────────────────┤
  │ 连接关闭 │ 发送 0\r\n 结束 chunk      │ 有标准 Close 帧，支持状态码和原因 │
  └──────────┴────────────────────────────┴───────────────────────────────────┘

  性能

  ┌──────────────┬──────────────────────────────┬────────────────────────────────┐
  │     维度     │         HTTP Chunked         │           WebSocket            │
  ├──────────────┼──────────────────────────────┼────────────────────────────────┤
  │ 头部开销     │ 只有第一次请求有 HTTP 头     │ 握手一次后，每帧仅 2-14 字节头 │
  ├──────────────┼──────────────────────────────┼────────────────────────────────┤
  │ 双向通信开销 │ 客户端要说话必须新建请求     │ 直接发帧，零额外开销           │
  ├──────────────┼──────────────────────────────┼────────────────────────────────┤
  │ 二进制支持   │ 需要 Base64 编码（膨胀 33%） │ 原生二进制帧                   │
  └──────────────┴──────────────────────────────┴────────────────────────────────┘

  三、各自适合的场景

  HTTP Chunked 适合

  ✅ 服务端单向推送，客户端只需要"听"
  ✅ 希望最大兼容性，不想折腾基础设施
  ✅ 事件频率不太高（秒级）

  ┌──────────────────────────┬──────────────────────────────────────────┐
  │           场景           │             为什么选 Chunked             │
  ├──────────────────────────┼──────────────────────────────────────────┤
  │ K8s Watch                │ 客户端只需监听资源变更，不需要反向发消息 │
  ├──────────────────────────┼──────────────────────────────────────────┤
  │ Server-Sent Events (SSE) │ SSE 底层就是 Chunked，浏览器原生支持     │
  ├──────────────────────────┼──────────────────────────────────────────┤
  │ 日志流式输出             │ docker logs -f、CI/CD 构建日志           │
  ├──────────────────────────┼──────────────────────────────────────────┤
  │ LLM 流式响应             │ ChatGPT/Claude 的逐 token 输出           │
  ├──────────────────────────┼──────────────────────────────────────────┤
  │ 大文件下载               │ 边生成边传，不需要提前算总大小           │
  └──────────────────────────┴──────────────────────────────────────────┘

  WebSocket 适合

  ✅ 双向实时通信
  ✅ 高频消息（毫秒级）
  ✅ 需要二进制数据传输
  ✅ 客户端和服务端都需要主动发消息

  ┌───────────────┬───────────────────────────────────────┐
  │     场景      │          为什么选 WebSocket           │
  ├───────────────┼───────────────────────────────────────┤
  │ 即时通讯/聊天 │ 双方都要随时发消息                    │
  ├───────────────┼───────────────────────────────────────┤
  │ 多人协作编辑  │ Google Docs —— 高频双向同步光标和文字 │
  ├───────────────┼───────────────────────────────────────┤
  │ 在线游戏      │ 毫秒级双向交互，二进制数据            │
  ├───────────────┼───────────────────────────────────────┤
  │ 实时交易/行情 │ 高频推送 + 客户端随时下单             │
  ├───────────────┼───────────────────────────────────────┤
  │ 远程终端      │ kubectl exec —— stdin/stdout 双向流   │
  └───────────────┴───────────────────────────────────────┘

  四、决策树

  需要客户端向服务端发消息吗？
  │
  ├── 不需要（纯服务端推送）
  │   │
  │   ├── 浏览器环境？ ──► SSE（基于 Chunked，有自动重连）
  │   │
  │   └── 后端服务间？ ──► HTTP Chunked（最简单，K8s 的选择）
  │
  └── 需要（双向通信）
      │
      ├── 高频 / 二进制 / 低延迟？ ──► WebSocket
      │
      └── 低频双向？ ──► 也可以用 WebSocket
                        或者两条 HTTP 连接凑合

  五、一个有趣的例子：kubectl exec

  kubectl exec -it pod -- /bin/bash

  实际上用的是 WebSocket（或 SPDY）：

    kubectl ──WebSocket──► apiserver ──WebSocket──► kubelet ──► 容器

  因为终端需要：
    stdin  → 用户键盘输入（客户端→服务端）
    stdout → 命令输出（服务端→客户端）
    stderr → 错误输出（服务端→客户端）
    resize → 窗口大小变化信号

    → 典型的双向、多路复用场景，Chunked 搞不定

  ▎ 一句话总结：Chunked 是"HTTP 框架内的单向流"，简单可靠兼容好；WebSocket 是"跳出 HTTP 的全双工通道"，强大但基础设施成本更高。能用 Chunked 解决就别上 WebSocket。
