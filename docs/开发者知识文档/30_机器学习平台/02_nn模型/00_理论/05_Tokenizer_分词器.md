
## 业界实践：大多数人不训练自己的分词器

  三种情况

  1. 直接复用现有的        ← 90% 的人这么做
  2. 基于现有的扩展/微调   ← 少数场景
  3. 从头训练             ← 只有大厂训基础大模型时才做

  ---
  情况一：直接复用（绝大多数人）

  微调模型时，必须用原模型的 Tokenizer，不能换：

  用 LLaMA 做微调 → 必须用 LLaMA 的 Tokenizer
  用 BERT 做下游任务 → 必须用 BERT 的 Tokenizer
  用 Qwen 做 RAG → 必须用 Qwen 的 Tokenizer

  原因很简单：Tokenizer 和 Embedding 是绑定的，换了 Tokenizer，所有 token ID 的含义都变了，等于模型的"眼睛"瞎了。

  ---
  情况二：扩展词表（少数场景）

  在原有 Tokenizer 基础上新增一些 token：

  # 典型场景：给模型加特殊标记或领域词汇
  tokenizer.add_tokens(["<用户>", "<系统>", "<工具调用>"])
  tokenizer.add_tokens(["BRCA1", "PD-L1", "mRNA"])  # 生物医学术语

  # 对应地，Embedding 矩阵也要扩展几行
  model.resize_token_embeddings(len(tokenizer))

  适用于：
  - 模型把你的领域术语切得太碎（如 BRCA1 → ["BR", "CA", "1"]）
  - 需要特殊控制标记

  ---
  情况三：从头训练（极少数）

  只有在训练基座模型时才需要，因为要针对目标语料优化切分效率：

  ┌──────────┬────────────────────┬────────────────────────────────────┐
  │   模型   │ 谁训练的 Tokenizer │           为什么要自己训           │
  ├──────────┼────────────────────┼────────────────────────────────────┤
  │ GPT-4    │ OpenAI             │ 英文为主的语料分布                 │
  ├──────────┼────────────────────┼────────────────────────────────────┤
  │ Qwen     │ 阿里               │ 中英文混合，需要中文切分效率高     │
  ├──────────┼────────────────────┼────────────────────────────────────┤
  │ LLaMA    │ Meta               │ 英文为主，后来社区扩展了中文 token │
  ├──────────┼────────────────────┼────────────────────────────────────┤
  │ DeepSeek │ DeepSeek           │ 中英文 + 代码混合                  │
  └──────────┴────────────────────┴────────────────────────────────────┘

  训练一个 Tokenizer 本身很快（几小时），但后果很重——它决定了整个模型的词表，后面所有训练都基于它。

  ---
  为什么不是每个人都训一个

  成本收益分析：

  自己训 Tokenizer
    → 必须从头预训练模型（几百万美元 + 几千张 GPU）
    → 因为 Tokenizer 换了，旧模型权重全部作废

  复用已有 Tokenizer
    → 可以站在已有模型的肩膀上微调
    → 几乎零成本

  核心原因：Tokenizer 和预训练权重绑定，换 Tokenizer = 放弃所有预训练成果。

  ---
  什么时候才值得从头训

  满足以下条件才考虑：

  1. 你有资源从头预训练一个基座模型
  2. 现有 Tokenizer 对你的语言/领域效率很低
  3. 效率差异大到值得付出这个代价

  例：LLaMA 原始词表对中文很不友好
     "机器学习" → ["机", "器", "学", "习"]  4 个 token

     Qwen 的词表专门优化了中文
     "机器学习" → ["机器学习"]              1 个 token

     同样的中文内容，LLaMA 消耗的 token 数量是 Qwen 的 3-4 倍
     → 上下文窗口利用率低，推理成本高
     → 所以中国大厂都选择自己训 Tokenizer

  ---
  总结

  ┌────────────────────────┬────────────────────────────────────┐
  │        你的角色        │                做法                │
  ├────────────────────────┼────────────────────────────────────┤
  │ 用开源模型做微调/应用  │ 直接用模型自带的 Tokenizer，不要动 │
  ├────────────────────────┼────────────────────────────────────┤
  │ 模型在你的领域切分太碎 │ 扩展几个专有 token，几行代码搞定   │
  ├────────────────────────┼────────────────────────────────────┤
  │ 大厂从头训基座大模型   │ 自己训 Tokenizer，针对语料分布优化 │
  └────────────────────────┴────────────────────────────────────┘

  ▎ 99% 的从业者不需要训练 Tokenizer。 它是基座模型的"基建"，由训练基座模型的团队一次性完成，其他人在此基础上复用。

## 只有语言模型才需要分词器吗？不是，但几乎只有处理"离散符号序列"时才需要

  核心判断标准

  输入是离散符号（文字、代码、分子式...）→ 需要某种 Tokenizer
  输入是连续数值（像素、音频波形、传感器...）→ 不需要

  ---
  各类模型的情况

  ┌─────────────────┬───────────────┬───────────────────┬───────────────────────────┐
  │      领域       │   输入类型    │ 需要 Tokenizer 吗 │         怎么处理          │
  ├─────────────────┼───────────────┼───────────────────┼───────────────────────────┤
  │ NLP / LLM       │ 文本          │ 需要              │ BPE / WordPiece           │
  ├─────────────────┼───────────────┼───────────────────┼───────────────────────────┤
  │ 代码模型        │ 代码文本      │ 需要              │ BPE（对代码优化）         │
  ├─────────────────┼───────────────┼───────────────────┼───────────────────────────┤
  │ 图像分类（CNN） │ 像素矩阵      │ 不需要            │ 直接输入连续数值          │
  ├─────────────────┼───────────────┼───────────────────┼───────────────────────────┤
  │ 图像生成（ViT） │ 像素          │ 类似需要          │ 切成 patch（类比分词）    │
  ├─────────────────┼───────────────┼───────────────────┼───────────────────────────┤
  │ 语音识别        │ 音频波形      │ 不需要原始分词    │ 先转频谱图/特征，连续输入 │
  ├─────────────────┼───────────────┼───────────────────┼───────────────────────────┤
  │ 推荐系统        │ 用户ID/行为   │ 不需要            │ 直接 Embedding 查表       │
  ├─────────────────┼───────────────┼───────────────────┼───────────────────────────┤
  │ 蛋白质模型      │ 氨基酸序列    │ 需要              │ 每个氨基酸就是一个 token  │
  ├─────────────────┼───────────────┼───────────────────┼───────────────────────────┤
  │ 基因模型        │ DNA序列       │ 需要              │ k-mer 或 BPE              │
  ├─────────────────┼───────────────┼───────────────────┼───────────────────────────┤
  │ 音乐生成        │ 音符/MIDI     │ 需要              │ 音符事件作为 token        │
  ├─────────────────┼───────────────┼───────────────────┼───────────────────────────┤
  │ 化学模型        │ 分子式 SMILES │ 需要              │ 字符级或子串              │
  └─────────────────┴───────────────┴───────────────────┴───────────────────────────┘

  ---
  规律

  本质问题：你的输入是否是"从一个有限集合中选出的符号组成的序列"？

  文本 = 从词汇表中选字组成句子          → 是 → 需要 Tokenizer
  代码 = 从关键字/标识符中选符号组成程序   → 是 → 需要 Tokenizer
  DNA  = 从 {A,T,G,C} 中选字母组成序列   → 是 → 需要 Tokenizer
  氨基酸 = 从 20种 中选组成蛋白质         → 是 → 需要 Tokenizer

  图像 = 连续的像素值                    → 否 → 不需要
  音频 = 连续的波形振幅                  → 否 → 不需要
  传感器 = 连续的物理量                  → 否 → 不需要

  ---
  有意思的趋势：连续数据也在"token 化"

  近年来有个趋势——把连续数据也强行变成离散 token，这样就能复用 Transformer 架构：

  图像：
    原始像素 → VQ-VAE 压缩 → 离散 code → 当 token 用
    （DALL-E 1、Parti 这样做）

    原始像素 → 切成 16x16 patch → 每个 patch 当一个 "token"
    （ViT、GPT-4V 这样做）

  音频：
    波形 → Encodec 压缩 → 离散 code → 当 token 用
    （AudioLM、MusicGen 这样做）

  视频：
    帧序列 → 每帧切 patch → patch 序列当 token
    （Sora 这样做）

  这些本质上都是在做 "连续数据的 Tokenizer"——只不过不叫 Tokenizer，叫 encoder / quantizer / patchify。

  ---
  一句话总结

  ▎ Tokenizer 不是语言模型专属，而是一切离散符号序列都需要。连续数据本来不需要，但现在也在被"token 化"以复用 Transformer 架构——广义上，任何把原始输入切成离散单元的过程都是 Tokenizer。
