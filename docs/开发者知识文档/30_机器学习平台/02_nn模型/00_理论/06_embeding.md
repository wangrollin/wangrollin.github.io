    2. Sentence Embedding 服务化

    现在更常见的做法，尤其在 RAG 和向量检索场景：

    模型外部：调用 Embedding API/服务
    "用户查询" → 调用 text-embedding-3-small → [0.23, -0.41, ...] → 存入向量数据库

    模型内部（下游任务）：直接用这个向量做检索/分类

    OpenAI 的 Embedding API、Sentence-BERT、BGE 等都是这种用法。向量算好就存起来，下游模型不再更新它。

    3. 推荐系统中的预训练 Item Embedding

    大厂常见做法：

    - 先用 Word2Vec 的思路（如 Item2Vec）在行为日志上预训练商品向量
    - 把向量存到 Feature Store 里
    - 下游推荐模型直接读取，冻结不训练

    判断标准

    ┌────────────────────────────────┬────────────────────────────────────────────┐
    │              场景              │               Embedding 放哪               │
    ├────────────────────────────────┼────────────────────────────────────────────┤
    │ 需要和模型一起端到端优化       │ 模型内部（nn.Embedding，参与训练）         │
    ├────────────────────────────────┼────────────────────────────────────────────┤
    │ 已有高质量预训练向量，冻结使用 │ 模型外部（预计算，当作特征输入）           │
    ├────────────────────────────────┼────────────────────────────────────────────┤
    │ 向量需要被多个模型/服务共享    │ 模型外部（作为公共服务或存 Feature Store） │
    └────────────────────────────────┴────────────────────────────────────────────┘

    所以你的直觉是对的：Embedding 一旦不需要学习，它和特征工程的边界就模糊了，都变成了"模型外部预计算好的数值输入"。
